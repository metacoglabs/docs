You're building a product where each customer or end user has private memory. Most teams want Pattern A.

<Warning>
  **Don't partition end users by `session_id`.** A key-only client (`Tex(api_key=...)` without `user_id`) acts as a single identity. `recall` searches everything that identity can see, whatever `session_id` you pass. Encoding the end user into `session_id` mixes every user's memory together and lets any user recall it all.
</Warning>

## Pattern A — one key, per-user clients (recommended)

You hold one Tex API key in your secrets manager. For each end user, build a client with `user_id=` and cache it. The SDK makes one `POST /auth/token-exchange` for that user and gets a token bound to them. Every call on that client — `remember`, `recall`, `documents.*`, `memories.*`, `search.*` — then acts as that user only.

The key needs an **impersonation scope**, normally `impersonate_user`. Owner keys with `"*"` also qualify. Without one, the SDK raises `PermissionDeniedError`. See [Per-user clients](/sdk/per-user-clients).

```python deps.py
import os
from functools import lru_cache

from tex import Tex


@lru_cache(maxsize=4096)
def tex_for_user(user_id: str) -> Tex:
    return Tex(
        api_key=os.environ["TEX_API_KEY"],
        base_url=os.environ["TEX_BASE_URL"],
        org_id=os.environ["TEX_ORG_ID"],   # required on SDK 1.2.0–1.2.1; recommended on 1.2.2+; must match the key's org
        user_id=user_id,
    )
```

```python chat.py
from fastapi import APIRouter, Depends
from .deps import tex_for_user

router = APIRouter()


@router.post("/chat")
def chat(body: ChatBody, user=Depends(current_user)):   # your auth dependency
    tex = tex_for_user(user.id)          # isolation comes from the identity
    sid = body.session_id                # session_id just groups one conversation

    hits = tex.recall(body.text, session_id=sid)
    answer = your_llm(body.text, memory=hits)
    tex.conversations.remember(turns, session_id=sid)
    return {"answer": answer}
```

| Trait | Pattern A |
| --- | --- |
| Tex keys to manage | 1 (server-side only) |
| Memory isolation | Per Tex user identity. A per-user token can't act for anyone else. |
| Sharing | Opt-in, through [scopes](/sdk/scopes) (`team:`, `project:`, `org:`) |
| Quota | Shared: one org, one daily quota |
| Cost of isolation | One token exchange per cached client |

<Note>
  Use stable, opaque user ids made of `[A-Za-z0-9_-]`, such as your database UUIDs. On Supermemory-compatible calls, a per-user client's `container_tag` must be omitted or equal that user id. Naming a different user returns `403 container_tag_not_permitted`.
</Note>

<Warning>
  An impersonation-capable key can mint a token for **any** user in your org. Keep it on your servers and never ship it to browsers or devices. For client-side apps, have your backend hand out short-lived per-user tokens. See the [ReM integration guide](/integrations/rem).
</Warning>

### Shared memory between users

Write into a shared scope and grant memberships:

```python
tex_for_user("alice").conversations.remember(turns, session_id=sid, scope="team:support")
tex_for_user("bob").recall("refund policy?", session_id="s-9")                       # sees team:support if bob is a member
tex_for_user("bob").recall("refund policy?", session_id="s-9", scope="team:support")  # narrow to that scope
```

A write or narrowed read into a scope the user isn't a member of returns `403 scope_not_visible`. Grant memberships from your org admin key with `tex.scopes.grant(user_id, "team:support")` (`POST /me/scope-memberships`). See [Managing memberships](/sdk/scopes#managing-memberships).

## Pattern B — one Tex org per end customer

Use this when each customer needs a hard org boundary, with separate quotas and separate keys.

```python signup.py
import httpx


def onboard_customer(label: str) -> dict:
    """Create a fresh Tex org for this customer. Persist org_id + key in your DB."""
    resp = httpx.post(
        "https://api.getmetacognition.com/signup",
        json={"name": label},
    )
    resp.raise_for_status()
    data = resp.json()            # api_key is shown once — store it encrypted
    db.customers.update(label, tex_api_key=data["api_key"], tex_org_id=data["org_id"])
    return data
```

Then, per request, look up that customer's key and org and build per-user clients inside it, exactly as in Pattern A:

```python
def tex_for(customer_id: str, user_id: str) -> Tex:
    row = db.customers.get(customer_id)
    return Tex(
        api_key=row.tex_api_key,
        base_url=os.environ["TEX_BASE_URL"],
        org_id=row.tex_org_id,
        user_id=user_id,
    )
```

Cache clients per `(customer_id, user_id)` in a TTL'd dict so you reuse connections.

| Trait | Pattern B |
| --- | --- |
| Tex keys to manage | One per customer, stored in your DB |
| Memory isolation | Org boundary plus per-user identities inside it |
| Quota | Separate daily quota per org |

<Note>
  `/signup` is an open endpoint. Put your own auth and abuse checks in front of any flow that calls it.
</Note>

## Quota strategy under Pattern A

Daily quotas are per org: 1,000,000 `tokens_in` and 5,000,000 `tokens_out` per UTC day, with `429` when exceeded. Under Pattern A, all end users share one quota, so one runaway user can starve the rest.

Mitigations:
- Track per-user token usage yourself. The `usage` field on every `remember` and `recall` response makes this cheap.
- Soft-cap each user at, say, 10% of the daily limit, then switch them to no-memory generation.
- Use [`tex.usage.today()`](/sdk/usage) to gate non-essential paths when total usage passes 90%.
